# Integration test run, 21 September 2026

A live smoke test of the real FastAPI → ChromaDB → Ministral chain. The contract HTTP tests used
the standard stubs; every check of `/query`, `/dashboard`, `/health` and `/predict` below ran
against the real local services and artifacts.

This is a historical record. At the time search ran on ChromaDB and sentence-transformers; since
November it runs on an own index and an ONNX model (ARCHITECTURE § 7.23). The questions were asked
in Russian; the answers are quoted in translation.

## 4. Normal corpus question

Question:

> How does oxygen concentration affect the burning rate?

The generated answer, HTTP 200 in 21.808 seconds:

> The burning rate depends on the regime:
> - **Thermally thin layer** → inversely proportional to the fuel surface density ([doc_id, p. 91]).
> - **Thermally thick layer** → does not depend on the density ([doc_id, p. 91]).
>
> Under **critical oxygen limitation** → a curved front (a larger area) helps combustion in an atmosphere with 21% O₂ ([doc_id, p. 97]). For a CO₂-diluted atmosphere in microgravity, combustion is stable at 21% O₂, while in normal gravity it is not ([doc_id, p. 97]).

Retrieved sources:

1. `NTRS-20000030678-Cooperative-Research-Projects-in-the-Microgra`, page 91
2. `NTRS-20000030678-Cooperative-Research-Projects-in-the-Microgra`, page 97
3. `NTRS-20210011385-Burning-and-Suppression-of-Solids-II-BASS-II-`, page 138

Assessment: **WARNING**. The claims trace back to pages 91 and 97, and the model added no
unsupported numbers. However, the most direct findings of the retrieved chunks did not make it into
the answer: as oxygen concentration rises, ignition delay decreases and flame temperature rises.
Also, instead of real document ids the model printed the literal template `[doc_id, p. N]`.

The model did not invent Saffire-IV results and did not present these captions as supporting
evidence. This is the main hallucination check from `SMOKE-TEST.md`.

## An operational problem noticed

With warm-up disabled at start, initialising the embedding service made several metadata requests
to Hugging Face even though the model weights were already local. Because of that the cold health
request took 11.465 seconds, and a fully offline start could retry connections. Warm `/query`
requests in this run were not affected. (Since November there is no Hugging Face library at run
time: the model is read from `data/embedding`.)
